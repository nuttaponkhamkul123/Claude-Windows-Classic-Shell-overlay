Vault view: improvement plan

The contact list's default view: each workspace is an underground room, and every chat is a robot inside it. Today (13 Nov 2026) it looks good, but it hides too much. This plan fixes that first, then makes the rooms actually tell you what each robot is doing.

1 · Where it stands today

What already works well: ✓ robots keep their colour and outfit · ✓ working robots act out their tool (hammer, desk, book…) · ✓ idle robots wander and fidget · ✓ needs-you robots show a “!” · ✓ furniture is seeded per workspace so it doesn't jump around.

2 · Where it's going

One floor per workspace, split into rooms by what's being done: a workshop (editing, commands), a study (reading, searching, web), a rest room (idle) and an approval gate. Each robot walks to the room that matches its current step, so every robot is always in the right place. A header strip brings back the name, counts, collapse and the ⋯ menu.

Busy workspace + collapsed one. Up to 6 robots on the floor; the rest sit in a drawer underneath as small clickable chips, so every chat is reachable. Collapsed workspaces keep their header with live counts.

3 · The plan

Phase 1 · Nothing hiddensmall · about a day

Fix the three high-severity problems before adding anything.

  • Show a slim header strip above each room in Vault view: caret, name, “2 running · 1 needs you · 5”, ⋯ menu. Clicking it collapses or expands, same as List view. ui/styles/features.css (stop hiding .workspace-header), ui/app.js renderSessionCards
  • Overflow drawer: chats beyond the 6 on the floor appear under the room as small avatar chips; clicking one opens the chat. buildWorkspaceVaultRoom: turn .vault-more into a drawer
  • Right-click a robot = the same menu as a list row (rename, pin, open folder, close…). Reuse the row's menu code instead of copying it. Pull the row's context-menu handler out of buildSessionCard into a shared function
  • Robots become buttons: Tab moves between them, Enter opens the chat, and the tooltip shows the chat title and its latest message.

Done when: every chat in every workspace can be opened, renamed and pinned from Vault view, including collapsed workspaces and workspaces with more than 6 chats.

Phase 2 · Calm, cheap updatessmall–medium · 1–2 days
  • Update rooms in place: keep each robot's element (keyed by chat id) and change only its pose, position and labels. Rebuild a room only when chats are added or removed. Same approach as the activity card's dataset.look check
  • Pause the idle-wander timer and all room animations when the HUD is hidden, minimised or showing a chat (document.hidden + a class on body).
  • Add a light room palette for Windows 7 / XP (pale walls, steel-blue frame), keeping the dark one for Vista Dark / Dark.

Done when: a robot walking across the room doesn't restart when another chat updates, and the HUD uses no measurable CPU while hidden.

Phase 3 · Rooms by activitymedium · 2–3 days
  • Split each floor into fixed rooms: Workshop (Edit, Write, Bash), Study (Read, Grep, Glob, web), Rest (idle), plus an Approval gate that only appears when a chat needs you. The room no longer depends on a “lead” robot.
  • When a robot's tool changes, it walks (or runs) from its current room to the new one instead of teleporting. It walks along the floor, using the existing pose-walk and left transitions.
  • A one-line label under each working robot: the tool plus a short target (“Bash · npm test”, “Read · app.js”), from describeActivity().
  • At the approval gate, the robot raises its hand (the “wait” pose from agent-stage.html) with Allow / Deny buttons right there, using the same approval handling as the toast.
  • Helper agents from the team stage follow their lead robot as small robots in the same room.

Done when: with three chats doing different things, each robot stands in the room that matches its step, and approving from the gate works.

Phase 4 · Nice to haveoptional
  • Floor gauges under the header: context used, tokens and cost today for that workspace (real numbers from usage.js, not a game economy).
  • Drag a robot to another workspace's floor to pin it there, or onto the gate to “ask for attention”.
  • A “done” moment: when a chat finishes, its robot waves a ✓, then walks to the rest room.
  • Zoom: Ctrl+scroll switches between big rooms and a dense “many workspaces” mode.

4 · Keep it ours

The view is inspired by base-building games (cut-away rooms, little workers), and that genre is fine to borrow from. To keep it an original design rather than a copy of a specific game:

  • Keep our own robots, furniture (GPU racks, diff desks, MCP docks) and room names. Don't use another game's characters, logos, mascots, door shapes or colour scheme.
  • Rename the code comment and plaque wording that names a specific game (features.css line ~1019, “Fallout Shelter–style…”). Calling it “Vault view” is fine.
  • Gauges show real HUD data (context, tokens, cost). Don't copy another game's resource system.

5 · Questions before starting

  • Room split: are Workshop / Study / Rest / Gate the right four, or should commands (hammering) get a room of their own?
  • Approving from the gate: should Allow / Deny live on the floor, or only open the chat?
  • Robots per floor: 6 visible plus a drawer, or should the floor get wider and scroll sideways?
